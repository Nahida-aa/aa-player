# 排查播放「无响应」与「卡顿」的经历

记录 player-app 从「打开就无响应」到「稳定 30fps」的完整排查过程。

> **核心教训：三次弯路，全部源于度量本身在骗人。**
> 每一次我都以为在调播放，实际上在调一个坏掉的仪表盘。日志埋错位置的
> 危害不是「少了信息」，而是**主动提供错误信息**，把人推向错误方向。

---

## 1. 症状与真因对照

按时间顺序，四个症状其实是四个独立的 bug：

| 症状 | 真因 | 修法 |
| --- | --- | --- |
| 画面静止在最后一帧 | 所有帧 `pts` 都是 0 | PTS 取 `raw_frame`，不是 scaler 输出帧 |
| 打开就无响应 | 同步 `recv()` 阻塞了 GPUI executor | 换 `futures::channel::mpsc` 异步收 |
| 播放卡顿（真） | 队列满时**静默丢帧** | 重试到送出为止，形成背压 |
| 播放忽快忽卡 | 落后后时间轴原点不修正 | 落后超阈值则重置原点 |

---

## 2. 陷阱一：scaler 输出帧不带 PTS

现象是画面不动。以为是渲染没触发，实际是**每一帧的时间戳都是 0**。

```rust
// 错误：swscale 生成的输出帧没有时间戳，恒为 None
let pts = self.rgba_frame.timestamp();

// 正确：时间戳只存在于解码器产出的原始帧上
let pts = self.raw_frame.timestamp();
```

> **原则**：像素格式转换只搬像素，不搬元数据。经过任何 filter/scaler 之后，
> 时间戳都要重新确认来源。

---

## 3. 陷阱二：阻塞 GPUI executor

worker 线程用 `std::sync::mpsc`，渲染侧 `rx.recv()` 同步等待——
GPUI 的 async task 跑在 executor 上，同步阻塞会**整个卡死事件循环**，
表现为窗口完全无响应。

```rust
// 错误：阻塞 executor
let frame = rx.recv().unwrap();

// 正确：异步让出
while let Some(item) = rx.next().await { ... }
```

> **原则**：async 上下文里禁止任何同步阻塞调用。`recv()`、`lock()` 长期持有、
> `thread::sleep` 都算。

另外 `FfmpegSource` 不是 `Send`（ffmpeg 的 `Scaler` 等类型没实现），
不能跨线程移动。解法是只把 `PathBuf` 传进线程，**在线程内部 open**。

---

## 4. 陷阱三：静默丢帧（真正的卡顿源）

这是最隐蔽的一个。

```rust
// 错误：满了就重试一次，还满就把帧扔了
if let Err(e) = tx.try_send(frame) {
    thread::sleep(Duration::from_millis(4));
    let _ = tx.try_send(e.into_inner());   // ← 失败即丢弃
}
```

关键认知：**队列满是常态，不是异常。** 渲染侧按 PTS 主动等待，
容量 3 的队列本来就该几乎总是满的——这正是我们要的背压
（防止解码跑在渲染前面太多）。把「常态」当「异常」处理，就成了持续丢帧。

丢帧的后果不只是少几帧，而是**渲染侧收到的 PTS 出现空洞**，
时间轴对不上，表现为忽快忽卡。

```rust
// 正确：重试到送出为止
let mut item = Some(frame);
while running.load(Ordering::Relaxed) {
    match tx.try_send(item) {
        Ok(()) => break,
        Err(e) if e.is_full() => {
            item = e.into_inner();
            thread::sleep(Duration::from_millis(2));
        }
        Err(_) => return,   // 接收端关闭
    }
}
```

## 5. 陷阱四：时间轴原点不可恢复

```rust
// 错误：原点定死在首帧，永不修正
let start = *play_start.get_or_insert_with(Instant::now);
```

一旦启动抖动或系统卡顿让播放落后，之后**每一帧都判定为「已迟到」**，
于是不再等待、全速冲刷，冲完再干等下一帧。这就是「忽快忽卡」。

正确做法是落后超过阈值时重置原点，让播放从当前位置继续：

```rust
} else if elapsed - target > Duration::from_millis(200) {
    warn!(behind_ms = ..., "播放落后，重置时间轴原点");
    play_start = Some(Instant::now() - target);
}
```

注意首帧的原点要减去它自己的 pts（`Instant::now() - target`），
因为首帧 pts 未必是 0。

> 这条 `warn` 是有意保留的信号：**稳态播放不该出现它**。
> 若持续刷屏，说明解码或渲染真的跟不上，要查根因而不是靠重置掩盖。

## 6. 度量的三次失败（最值得记的部分）

### 6.1 计数器埋在错误的分支

```rust
if let Err(e) = tx.try_send(...) {
    ...                                    // 丢帧路径：不计数
} else {
    profile.record_decoded(decode_us);     // ← 只有成功才计数
}
```

队列持续满 → 一直走 `if` 分支 → `decoded/s` 显示 **0**。

于是我得出结论「worker 线程死了」，并花时间去查 `PacketIter` 是否把
I/O 错误误报成 EOF。**worker 一直活着，死的是计数器。**

同一份统计里 `drop_rate` 显示 `0%`——因为它的算法是
`(decoded - displayed) / decoded`，`decoded` 归零时恒为 0。
一个专门用来发现丢帧的指标，在丢帧最严重时显示「没有丢帧」。

> **原则**：计数器要放在**事件真实发生处**，不能挂在某个条件分支上。
> 尤其是「失败/丢弃」路径，恰恰最需要被计数。

### 6.2 直方图桶太粗，判据形同虚设

第一版桶：`[20, 30, 36, 45, 66, 100]`，判据 `p99 > 45`。

输出里 p99 **每一行都恰好是 45**。不是巧合——分位数落在 `36~45` 桶
只能报桶上界 45，而 `45 > 45` 永远为假。**这条判据从来没有触发过。**

改成 9 个密集桶 `[20, 28, 32, 35, 38, 42, 50, 66, 100]` 后才有分辨率。

> **原则**：桶边界要密集分布在**关心的值附近**（30fps 即 33.3ms），
> 不能等宽。等宽桶会把 33 和 40 归为一类，恰好看不见要找的抖动。
> 同时判据用 `>=` 而非 `>`，否则边界桶永远不触发。

### 6.3 阈值过严导致告警疲劳

细化后发现每 2 秒有 1 帧晚到 6ms（39ms），被判为卡顿。
但这是 timer 精度与合成器节拍的正常抖动，肉眼完全不可感。

> **原则**：阈值按**人的感知**定，不按理论完美定。
> 告警天天响，真出问题时反而会被忽略。

## 7. 最终的判据

平均值会把偶发卡顿完全抹平——这正是早期没能定位问题的原因。
必须看**尾部分布**。

| 指标 | 含义 | 健康值 |
| --- | --- | --- |
| `on_time_pct` | 帧间隔落在 28~38ms 的占比 | 100% |
| `max_interval_ms` | 最坏间隔，> 66 即掉了整帧 | 35~38 |
| `avg_decode_us` | 单帧解码耗时（预算 33ms） | ~4000 |

```rust
let janky = max_i > 66 || on_time_pct < 90;
```

用法：

```bash
RUST_LOG=player_app=debug just dev
```

日志直接给结论（`INFO 播放流畅` / `WARN 检测到卡顿`），
不需要自己换算。卡顿时附带直方图便于定位。

## 8. 通用心得

1. **编译期强 ≠ 运行期正确。** 这四个 bug 全部「类型正确、编译通过」。
   Rust 消灭的是空指针和数据竞争，消灭不了逻辑与时序错误。
   播放器的正确性标准是「时间上准不准时」，纯运行时属性，静态分析够不着。

2. **先怀疑度量，再怀疑系统。** 三次弯路都是度量在骗人。当数据反直觉时
   （fps 突然归零、某指标恒为同一个值），先验证仪表本身。

3. **常态与异常要分清。** 队列满是设计意图，不是故障。把常态当异常处理，
   就制造了真正的故障。

4. **容差过松的测试等于没有测试。** seek 测试最初容差 12s，
   连「seek 落回 0 秒」这种明显错误都能通过。收紧到 1.5s 后才有意义
   （前提是测试素材有固定 GOP）。
