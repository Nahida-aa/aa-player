# 排查播放「无响应」与「卡顿」的经历

记录 aa-player 从「打开就无响应」到「稳定 30fps」的完整排查过程。

> **核心教训：三次弯路，全部源于度量本身在骗人。**
> 每一次我都以为在调播放，实际上在调一个坏掉的仪表盘。日志埋错位置的
> 危害不是「少了信息」，而是**主动提供错误信息**，把人推向错误方向。

---

## 1. 症状与真因对照

按时间顺序，四个症状其实是四个独立的 bug：

| 症状 | 真因 | 修法 |
| --- | --- | --- |
| 画面静止在最后一帧 | 所有帧 `pts` 都是 0 | PTS 取 `raw_frame`，不是 scaler 输出帧 |
| 打开就无响应 | 同步 `recv()` 阻塞了 GPUI executor | 换 `futures::channel::mpsc` 异步收 |
| 播放卡顿（真） | 队列满时**静默丢帧** | 重试到送出为止，形成背压 |
| 播放忽快忽卡 | 落后后时间轴原点不修正 | 落后超阈值则重置原点 |
| 读取出错却「正常播完」/ CPU 跑满 | 迭代器把 I/O 错误折叠成 EOF | 直接驱动 `Packet::read` 区分错误类型 |

---

## 2. 陷阱一：scaler 输出帧不带 PTS

现象是画面不动。以为是渲染没触发，实际是**每一帧的时间戳都是 0**。

```rust
// 错误：swscale 生成的输出帧没有时间戳，恒为 None
let pts = self.rgba_frame.timestamp();

// 正确：时间戳只存在于解码器产出的原始帧上
let pts = self.raw_frame.timestamp();
```

> **原则**：像素格式转换只搬像素，不搬元数据。经过任何 filter/scaler 之后，
> 时间戳都要重新确认来源。

---

## 3. 陷阱二：阻塞 GPUI executor

worker 线程用 `std::sync::mpsc`，渲染侧 `rx.recv()` 同步等待——
GPUI 的 async task 跑在 executor 上，同步阻塞会**整个卡死事件循环**，
表现为窗口完全无响应。

```rust
// 错误：阻塞 executor
let frame = rx.recv().unwrap();

// 正确：异步让出
while let Some(item) = rx.next().await { ... }
```

> **原则**：async 上下文里禁止任何同步阻塞调用。`recv()`、`lock()` 长期持有、
> `thread::sleep` 都算。

另外 `FfmpegSource` 不是 `Send`（ffmpeg 的 `Scaler` 等类型没实现），
不能跨线程移动。解法是只把 `PathBuf` 传进线程，**在线程内部 open**。

---

## 4. 陷阱三：静默丢帧（真正的卡顿源）

这是最隐蔽的一个。

```rust
// 错误：满了就重试一次，还满就把帧扔了
if let Err(e) = tx.try_send(frame) {
    thread::sleep(Duration::from_millis(4));
    let _ = tx.try_send(e.into_inner());   // ← 失败即丢弃
}
```

关键认知：**队列满是常态，不是异常。** 渲染侧按 PTS 主动等待，
容量 3 的队列本来就该几乎总是满的——这正是我们要的背压
（防止解码跑在渲染前面太多）。把「常态」当「异常」处理，就成了持续丢帧。

丢帧的后果不只是少几帧，而是**渲染侧收到的 PTS 出现空洞**，
时间轴对不上，表现为忽快忽卡。

```rust
// 正确：重试到送出为止
let mut item = Some(frame);
while running.load(Ordering::Relaxed) {
    match tx.try_send(item) {
        Ok(()) => break,
        Err(e) if e.is_full() => {
            item = e.into_inner();
            thread::sleep(Duration::from_millis(2));
        }
        Err(_) => return,   // 接收端关闭
    }
}
```

## 5. 陷阱四：时间轴原点不可恢复

```rust
// 错误：原点定死在首帧，永不修正
let start = *play_start.get_or_insert_with(Instant::now);
```

一旦启动抖动或系统卡顿让播放落后，之后**每一帧都判定为「已迟到」**，
于是不再等待、全速冲刷，冲完再干等下一帧。这就是「忽快忽卡」。

正确做法是落后超过阈值时重置原点，让播放从当前位置继续：

```rust
} else if elapsed - target > Duration::from_millis(200) {
    warn!(behind_ms = ..., "播放落后，重置时间轴原点");
    play_start = Some(Instant::now() - target);
}
```

注意首帧的原点要减去它自己的 pts（`Instant::now() - target`），
因为首帧 pts 未必是 0。

> 这条 `warn` 是有意保留的信号：**稳态播放不该出现它**。
> 若持续刷屏，说明解码或渲染真的跟不上，要查根因而不是靠重置掩盖。

## 6. 陷阱五：被抽象吞掉的错误

前面四个 bug 是自己写错，这个不一样——**是库的抽象主动隐藏了信息**。

`ffmpeg-next` 提供了很顺手的 packet 迭代器：

```rust
for (stream, packet) in input.packets() { /* ... */ }
```

问题在于 `PacketIter::next` 的实现把**所有**错误都折叠成 `None`：

```rust
// rust-ffmpeg 内部，简化后
match packet.read(input) {
    Ok(())               => Some(...),
    Err(Error::Eof)      => None,   // 真读完
    Err(_)               => None,   // 读挂了 —— 和读完长得一模一样
}
```

于是「网络断了」「磁盘读失败」和「正常播完」在调用方看来完全无法区分。
更糟的是后续的连锁反应：

1. `next_frame` 收到 `None`，以为到尾了，去 `send_eof()` 进入 draining；
2. 但终止性错误已经被记进 `AVIOContext->pb->error`，是**粘性**的；
3. 之后每次 `av_read_frame` 都立刻返回同一个错误；
4. 外层循环一直读、一直「失败」、一直重来 —— **98% CPU 空转，永不退出**。

一个被静默的错误，最终表现成了「界面卡死 + 风扇狂转」。

修法是绕开迭代器，自己驱动 `Packet::read`，把三种情况分开：

```rust
match packet.read(&mut self.input) {
    Ok(())                  => { /* 拿到包 */ }
    Err(Error::Eof)         => return Ok(None),  // 真结束
    Err(Error::InvalidData) => continue,         // 坏包，跳过重同步
    Err(e)                  => return Err(e.into()), // 终止性错误，上报
}
```

关键是 `InvalidData` 必须和其它错误分开：坏包是可恢复的（解复用器能重新
同步），无脑上报会让稍有瑕疵的文件直接播不了；而终止性错误必须上报且
**不能重试**，否则就是上面那个空转。

### 怎么验证它真的修好了

这个 bug 最难的不是修，是**构造出能触发它的场景**。试了三次才成功：

| 尝试 | 结果 | 为什么不行 |
| --- | --- | --- |
| 截断 mp4 | `open` 阶段就失败 | `moov` 在文件尾，压根进不了解码循环 |
| 截断 TS 文件 | 干净 EOF | 文件提前结束在 OS 层面就是正常 EOF，不是错误 |
| FIFO 提前关闭写端 | 干净 EOF | 同上，管道关闭 = EOF |
| concat 分片读到一半被截短 | 干净 EOF | 同上 |
| **HTTP 声明长度后中途断开** | **报错** | 协议层知道「还差一大截」，判定为连接中断 |

规律很清楚：**操作系统层面「没有更多字节了」就是 EOF，无法表达「本该还有」。**
只有声明了预期长度的协议才能发现缺斤少两。所以不是偷懒选了 HTTP，
是本地文件从物理上就造不出这个错误。

最后用一个内置的 `TcpListener` 假服务器：响应头里写 `Content-Length: 全长`，
实际只发 1/4 就关闭连接。ffmpeg 的 http 协议层发现数据不够，报
`Connection reset by peer`。

回归测试还有三个细节：

- **必须重封装成 TS**：mp4 截断后 `open` 就失败，测不到 `next_frame`。
  测试里用 `ffmpeg -c copy -f mpegts` 现场转，不额外存素材。
- **解码放子线程 + 超时**：错误被吞掉时的症状是死循环，直接在测试线程跑
  会把 CI 挂死。用 30s 看门狗把「卡死」转成一条明确的失败信息。
- **测试的需要不能倒逼生产代码放宽约束**。见下。

### 别让测试污染生产代码

最初为了让测试连上 HTTP，我改了 `open()`：把 `path.exists()` 检查改成
「带 `://` 的放行」。这是**顺序反了**——本该先有需求再有能力，
变成了先有测试再倒推出能力。副作用是 `rtsp://...` 这类源突然能进来了，
而这个能力从没被设计、也从没被测过，等于凭空多出一块无人负责的行为面。

正确做法是把构造逻辑拆出来，让测试从**下一层**进入：

```rust
fn open(path: &Path) -> Result<Self> {
    if !path.exists() { return Err(...) }        // 约束原样保留
    Self::from_input(ffmpeg_next::format::input(&path)?)
}

pub(crate) fn from_input(input: Input) -> Result<Self> { /* 构造逻辑 */ }
```

`open` 的行为一字未改，测试则绕过路径校验直接喂流。代价是 `from_input`
为 `pub(crate)`，所以这条测试必须写成 **crate 内的单元测试**
（集成测试 `tests/` 算外部 crate，看不到 `pub(crate)`）。

> **原则**：测试难写往往说明**接缝没切对**，而不是约束该放宽。
> 放宽约束是把测试的成本转嫁给了生产代码——而且这笔账在当时看不见。

验证方式是**把旧实现改回去跑一遍**：修复版 0.36s 通过，旧版 30s 超时失败。
一条没在坏代码上失败过的测试，不能算证明了任何事情。

## 7. 度量的三次失败（最值得记的部分）

### 7.1 计数器埋在错误的分支

```rust
if let Err(e) = tx.try_send(...) {
    ...                                    // 丢帧路径：不计数
} else {
    profile.record_decoded(decode_us);     // ← 只有成功才计数
}
```

队列持续满 → 一直走 `if` 分支 → `decoded/s` 显示 **0**。

于是我得出结论「worker 线程死了」，并花时间去查 `PacketIter` 是否把
I/O 错误误报成 EOF。**worker 一直活着，死的是计数器。**

同一份统计里 `drop_rate` 显示 `0%`——因为它的算法是
`(decoded - displayed) / decoded`，`decoded` 归零时恒为 0。
一个专门用来发现丢帧的指标，在丢帧最严重时显示「没有丢帧」。

> **原则**：计数器要放在**事件真实发生处**，不能挂在某个条件分支上。
> 尤其是「失败/丢弃」路径，恰恰最需要被计数。

### 7.2 直方图桶太粗，判据形同虚设

第一版桶：`[20, 30, 36, 45, 66, 100]`，判据 `p99 > 45`。

输出里 p99 **每一行都恰好是 45**。不是巧合——分位数落在 `36~45` 桶
只能报桶上界 45，而 `45 > 45` 永远为假。**这条判据从来没有触发过。**

改成 9 个密集桶 `[20, 28, 32, 35, 38, 42, 50, 66, 100]` 后才有分辨率。

> **原则**：桶边界要密集分布在**关心的值附近**（30fps 即 33.3ms），
> 不能等宽。等宽桶会把 33 和 40 归为一类，恰好看不见要找的抖动。
> 同时判据用 `>=` 而非 `>`，否则边界桶永远不触发。

### 7.3 阈值过严导致告警疲劳

细化后发现每 2 秒有 1 帧晚到 6ms（39ms），被判为卡顿。
但这是 timer 精度与合成器节拍的正常抖动，肉眼完全不可感。

> **原则**：阈值按**人的感知**定，不按理论完美定。
> 告警天天响，真出问题时反而会被忽略。

## 8. 最终的判据

平均值会把偶发卡顿完全抹平——这正是早期没能定位问题的原因。
必须看**尾部分布**。

| 指标 | 含义 | 健康值 |
| --- | --- | --- |
| `on_time_pct` | 帧间隔落在 28~38ms 的占比 | 100% |
| `max_interval_ms` | 最坏间隔，> 66 即掉了整帧 | 35~38 |
| `avg_decode_us` | 单帧解码耗时（预算 33ms） | ~4000 |

```rust
let janky = max_i > 66 || on_time_pct < 90;
```

用法：

```bash
RUST_LOG=player_app=debug just dev
```

日志直接给结论（`INFO 播放流畅` / `WARN 检测到卡顿`），
不需要自己换算。卡顿时附带直方图便于定位。

## 9. 通用心得

1. **编译期强 ≠ 运行期正确。** 这些 bug 全部「类型正确、编译通过」。
   Rust 消灭的是空指针和数据竞争，消灭不了逻辑与时序错误。
   播放器的正确性标准是「时间上准不准时」，纯运行时属性，静态分析够不着。

2. **先怀疑度量，再怀疑系统。** 三次弯路都是度量在骗人。当数据反直觉时
   （fps 突然归零、某指标恒为同一个值），先验证仪表本身。

3. **常态与异常要分清。** 队列满是设计意图，不是故障。把常态当异常处理，
   就制造了真正的故障。

4. **容差过松的测试等于没有测试。** seek 测试最初容差 12s，
   连「seek 落回 0 秒」这种明显错误都能通过。收紧到 1.5s 后才有意义
   （前提是测试素材有固定 GOP）。

5. **顺手的抽象可能在吞信息。** `for p in input.packets()` 读起来很自然，
   却把 I/O 错误和正常结束合并成了同一个 `None`。**返回类型比 API 好不好用
   更重要**：如果一个接口没法表达「失败了」，那它一定会在某个地方骗你。

6. **没在坏代码上失败过的测试，不算测试。** 新增回归测试后，一定要把旧的
   错误实现改回去跑一遍，确认它真的会红。否则很可能只是写了一条
   「无论如何都通过」的断言，白白换来虚假的安全感。

7. **测试写不进去，先怀疑接缝，别急着改约束。** 为了测试放宽生产代码的
   校验，是把成本转嫁给了线上行为。多数情况下正确解法是把逻辑拆出一层
   （如 `open` / `from_input`），让测试从下一层进入，而不是让上层变松。
